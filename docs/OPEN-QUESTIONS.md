## From the brief (section 9): to be answered by the agent test

| # | Question | Status | Answer |
|---|---|---|---|
| Q1 | Does the extension discover the tools and call them without clicking? | **Answered: yes** | Run 1 (2026-11-13): the side panel listed `sign_in` with our description, and the agent called it with the code from the prompt, then `get_product` and `create_checkout`, with no clicks on the page. See `test-runs/2026-11-13-1417-opus55-run1.md`. |
| Q2 | Does it follow `create_checkout`'s Stripe link to Stripe's page? If not, what failed exactly, and what would fix it (new tab, embedded Checkout, ...)? | **Answered: no (fix pending user decision)** | Run 1: the agent got the URL but "none of my tools can open or type into the Stripe checkout page". It stopped and offered a clickable link for the user. Cause: the extension has no tabs/navigation ability of its own and only exposes page tools. **But** its code supports a *page tool* that navigates or opens a tab, and then continues the conversation on the new page's tools (`extensionBridge.ts` `executeTabTool` / `onTabChanged`). Candidate fix: a session-protected tool that navigates the tab to the Stripe URL via script (the URL is still never in the DOM). Embedded Checkout would conflict with rule 3. |
| Q3 | Does Stripe's test Checkout page expose WebMCP tools? Which ones? | **Answered** | Yes, in a sandbox, from an **iframe**. DevTools lists six: `fill_payment_form`, `get_link_pay_token_merchant`, `get_order_summary`, `select_payment_method`, `set_link_pay_token`, `submit_payment`. Only 3 are exposed to the top frame (run 2), so the stock extension never sees `fill_payment_form`; local patch D20 fixes that. With card-only + Link off (D22), 4 tools: `get_order_summary`, `select_payment_method`, `fill_payment_form`, `submit_payment`. `fill_payment_form` fills the form but **never resolves** (DevTools: "In progress"). `get_order_summary` output is marked untrusted (spotlighted). |
| Q4 | Does the agent ask for confirmation before the consequential submit tool, as Stripe's docs say it should? | **Answered: yes (with a caveat)** | The extension always shows an Allow prompt for `submit_payment` (runs 2, 6). The model asked in chat each time before paying (runs 2, 4, 5, 6). Caveat from run 6: the model asked **in advance** (before the form was filled) and later submitted on that earlier "yes", without re-asking after `fill_payment_form` timed out twice. |
| Q5 | Can the agent retrieve the PDF through `get_download`? | **Answered: yes, via the page (D19)** | The stock agent can't open links. With D19, `get_download` itself fetches the single-use link and saves the file. Run 6: 596-byte PDF saved; `pdftotext` = exactly "You now own this PDF." The model only learns the size and that it's a PDF, not the text. |
| Q6 | (Optional control) What does Claude in Chrome do with the same task? | **Answered: it can't use the tools** | Not run in Phase 1. Run on the **live** site on 2026-11-17 (Chrome 157, no flag): it found the tools only by reading `app.js`, looked for `navigator.modelContext`, found nothing, and stopped without calling a tool. It declined to call the server directly. WebMCP was in fact on (`document.modelContext` with all 12 public tools). See `test-runs/2026-11-17-0840-claude-in-chrome.md`. |

## Raised during Step 0

| # | Question | Status | Answer |
|---|---|---|---|
| Q7 | Is `navigator.modelContext` officially deprecated? | Partly answered | Chrome docs only use `document.modelContext`. **In Chrome 157 with the origin trial, `navigator.modelContext` is undefined and `document.modelContext` exists** (probe, 2026-11-17). That matters in practice: Claude in Chrome checked the `navigator` name and wrongly concluded WebMCP was off. Not blocking: we use `document.modelContext`. |
| Q8 | Can a new Stripe account use test mode or a sandbox before activation? | **Answered** | **Yes.** Stripe docs: "Immediately after you create a Stripe account, you can use a sandbox… without moving any money." The user created an account, switched to a sandbox, created a restricted test key, and it worked for Checkout Sessions (2026-11-13). |
| Q9 | Does `wrangler dev` (purely local) require a Cloudflare login? | **Answered** | **No.** Wrangler 4.162.0 started and served `http://localhost:8787` with no login prompt and no Cloudflare account (2026-11-13, Step 2). |
| Q10 | Does inline `price_data` on Checkout Session create work as expected with API version `2026-10-28.endive`? | **Answered** | **Yes.** `line_items[0][price_data][currency/unit_amount/product_data][name]` created a hosted `cs_test_` session. A restricted key with **only "Checkout Sessions: Write"** was enough: no Products or Prices permission was needed, even though inline price data creates those objects behind the scenes. Retrieve also works with that key. |
| Q14 | How did Stripe's restricted-key screen differ from the docs? | Answered | The docs describe choosing per-resource permissions. The live screen first offers four choices: "Start with a template", "Custom permissions", "Full access—except sensitive operations", and "Full access" (labelled High risk). We chose **Custom permissions**, set Checkout Sessions to Write, and left everything else at None. |
| Q11 | Does Chrome accept the `Secure` session cookie on `http://localhost`? | **Answered** | **Yes.** In Chrome 157, after `sign_in` was run from the DevTools WebMCP pane, Application → Cookies showed `__Host-pdfs_session` with HttpOnly, Secure and SameSite=Strict (user check, 2026-11-13). The `__Host-` prefix is also accepted on localhost. |
| Q12 | Do tools registered after sign-in reach the extension mid-conversation? | **Answered: yes** | Run 1: the request right after `sign_in` offered all six tools. Original note: | The README says tools that appear during a conversation are "picked up before the next model turn" (via `toolchange`). Confirm in the agent test. |
| Q15 | Why doesn't the extension receive Stripe's `fill_payment_form`? | Open (diagnosed, not proven) | Run 2: visible in DevTools WebMCP on the Stripe tab, never in the side panel or the model's tool list (6 requests, about 1 hour). Stripe's tools live in a subframe (`_401_`). The extension re-lists only on the top document's `toolchange` and drops subframe reports (`useActiveTabTools.ts`). Next: check in the Console whether the top frame's `getTools()` includes `fill_payment_form` at all. |
| Q13 | Once live, does the design stop other people from spamming the site? (Asked by the user, 2026-11-13.) | Partly answered | **Yes, against:** buying anything; creating Stripe Checkout Sessions (which also blocks "card testing" fraud); and guessing codes (lockout). **No, against:** flooding the page or `sign_in` with requests (volume and cost). The global lockout can also be triggered on purpose to lock the owner out for 15 minutes. **For going live (Phase 2):** Cloudflare rate-limiting rules in front of the Worker, use the real client IP (`CF-Connecting-IP`), and reconsider the global lockout. |
