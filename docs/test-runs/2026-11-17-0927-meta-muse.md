- **Site:** https://pdfsupplier.com (live, version 5a88a012)

- **Where it ran:** the owner ran Muse on their **phone**. Muse browsed partly from the phone (page loads, `/robots.txt`, `/mcp`), but **made the purchase from Meta-side servers** (`curl/8.5.0`, Cloudflare network).

- **Looking for a machine-readable door first.** Muse identified itself honestly (`Muse-PersonalAgent/0.3`) and asked for `/.well-known/poppy.json`, apparently a site description format Meta's agents look for (Cloudflare's agent-readiness scan checks for the same file). From the owner's device it also tried `/mcp`, which looks like a check for an MCP server endpoint. Both are missing on this site.
- **Muse browsed partly from the owner's phone.** The phone's page loads and the `robots.txt` and `/mcp` requests came from the owner's own device. The purchase calls came from Meta-side servers (`curl`, Cloudflare network).
- **No `/api/session` after the phone's page loads**, so the phone's browser didn't run WebMCP. (A page load followed by `/api/session` is the sign of a WebMCP browser; see the Gemini write-up.)
- **`app.js` isn't logged**, but Muse must have read it: nothing else contains the addresses and field names it used.
- `GET /api/session` during the purchase was Muse copying a call the script makes (owner sign-in check), not a tool. That suggests it copied the script's behaviour, not just the tool list.

## What this run tells us

1. **The first outside agent to complete a purchase did it without WebMCP.** Muse didn't run in a browser that exposes `document.modelContext`. It made the same HTTP calls the tools make (paths, JSON bodies and the session cookie), most likely worked out from the page script, where each tool's code shows its call. **WebMCP tool definitions double as API documentation** for any agent that can read the script and send HTTP requests.
2. **This is the shortcut Claude in Chrome refused to take** ("I didn't fake the purchase by calling the site's back-end directly… I don't run payment steps that way"). Different agents draw that line in different places.
3. **The server-side walls still held.** Muse needed a session cookie, the store's single-use sandbox token, the session-bound single-use download link, and Stripe confirming payment. The "server is the gate" design (brief) is what made the direct route safe.
4. **The per-visitor limits saw 8 visitors, not 1**, because each request left from a different address. What still applies to an agent like this: the store-wide caps, the per-session order cap, and Stripe's single-use token. Recorded in `docs/SECURITY.md`.
5. **It asked permission before paying**, unprompted, even though the instruction said "complete a transaction".
6. **It's the first agent to use `say_hello`.**
7. Its description of the flow ("say hello, get a test payment, get the product details, then buy it and take delivery") follows the page text, not the order it actually used.

## Questions this raises
- Does Muse have a browser mode that sees WebMCP tools, or does it always work over HTTP? (Q18)
- Should the experiment count an HTTP-only purchase as a success? The server allows it by design, because the server is the gate and the tools are a front end to it. The owner decides how to score it. (Q20)
